# Succubus Club: working with the platform and its author

[Succubus Club](https://github.com/thomasWajs/succubus-club) (SC) is Thomas
Wajs's online VTES table. The fork (`../succubus-club`, remote `fork` =
lionel-panhaleux/succubus-club) plays engine games against
`engine.krcg.org`. This file is the log the `sc-change` skill reads and
updates: how Thomas works, the state of every PR, what we learned. Add to it
whenever something reaches us from Thomas or a PR moves.

## Thomas's working style (what we know)

- **Human-made contributions.** PR #207 (July 2026, another author) was
  closed: "This is quite obviously LLM-generated. … The wall of text
  generated by the LLM won't actually help any newcomer understand the
  project. … I'll be happy to review any human-made contribution." So what
  goes upstream is the owner's to stand behind: small and focused, reviewed
  by the owner, its text written or approved by the owner, short and plain,
  no long explanations, no emoji; AI involvement stays disclosed (the
  `Co-Authored-By` trailers are kept, never stripped). A PR is opened or
  answered only on the owner's word.
- **Commits**: short imperative subjects, often "Close #NNN" / "Fix #NNN",
  no body as a rule (his "Change card depth behaviour. Close #275"). The
  fork's long descriptive subjects ("Engine games: …") never go upstream.
- **AGENTS.md** is his rulebook for agents: Vue 3 `<script setup>`, Phaser 3
  via Phavuer; state changes only through `GameMutation`s; `src/shared`
  environment-agnostic; Pinia stores; no `any`, no `!` assertions, no
  semicolons, `@/` imports with extensions, LF, no emoji anywhere; SCSS, no
  `border-radius` on rectangles, no `box-shadow`, no `!important`; desktop
  only; checks `npm run type:check`, `lint:check`, `format:check`; agents do
  not start vite or validate rendering in a browser. `border-radius` and
  `box-shadow` are no, `!important` is "avoid".
- **Seen in the code, not in AGENTS.md**: comments with spaces inside
  parentheses `( like this )` and French typography (` :`); `card.markers`
  are players' free strings, the only numeric counters `greenCounter` /
  `orangeCounter`; per-mutation log lines through `History.addGameMutation`.
- **Told up front**: the owner warned Thomas in person about the AI
  involvement in #282–#285 (2026-10-14).
- **Unknown yet**: how he reviews, what he thinks of the engine game type.
  Record his first reactions to #282–#285 here.

## The integration's shape (online-plan §C, the owner's)

SC files get hooks only: one `useEngineMode()` (`src/client/engine/mode.ts`),
`useUIFeatures` flags (`manualControlsEnabled`, `automaticCostPaymentEnabled`),
one `<EngineCentral/>`; engine code in `src/client/engine/` and
`central/Engine*.vue`. Never `gameState.gameType == GameType.Engine` inline in
SC files. Engine-only display state lives in the engine store (`chips`,
`limbo`), not on SC's synced `Card`.

## The dev server

The owner plays on `http://localhost:5188`: vite serving the main
checkout's `zero-vtes-engine` against `engine.krcg.org` (no
`VITE_ENGINE_SERVER`). Z-play runs it, one session at a time:

- **At the session's start**: if nothing listens (`lsof -nP -iTCP:5188
  -sTCP:LISTEN` empty), start it as the session's background task, `cd
  ../succubus-club && npx vite --config vite/config.dev.mjs --port 5188
  --strictPort > $CLAUDE_JOB_DIR/tmp/vite.log 2>&1`, and check it answers
  (`curl -s -o /dev/null -w '%{http_code}' http://localhost:5188/` gives
  200). Something already listening is a previous session's server (a
  session cleared without warning) the owner may be playing on: tell the
  owner, and restart it on their word once they are not mid-game; never
  kill it unasked.
- **When the owner ends or clears the session** (the owner says so first):
  stop it once the owner is not mid-game, by its port: `kill $(lsof
  -tiTCP:5188 -sTCP:LISTEN)` (a `pkill -f` on vite's command line also
  matches the agent's own shell running it). The next session starts it
  anew.
- **In between**: never restarted without the owner's word (the fork
  cannot rejoin a game yet, traps below). After a restart the owner
  refreshes the tab (traps).

## Recipes

- **Re-cut** (fold the fork's later work into `engine-game`): cherry-pick the
  fork's commits onto the re-cut tip, resolve toward the re-cut's structure,
  check, tag the flat state; `reset --soft` to the old tip, `commit
  --fixup=<commit>` per file group (each file maps to exactly one re-cut
  commit), `git rebase --autosquash <base>`; `git diff <flat-tag> HEAD` must
  be empty; `vue-tsc` at every commit. Fork idioms the re-cut dropped
  (`GameType.Engine` inline, `short(...)!`) are translated, not copied: grep
  added lines for `GameType.`, `!.`, `!)`, `border-radius`, `box-shadow`,
  `!important`, emoji.
- **Diagnosis** from the server's record, not screenshots:
  `scripts/fetch_games.py --since … --out $CLAUDE_JOB_DIR/tmp/records`, then
  `cargo run -p zvtes-host --profile ci --example replay -- <record> --options`.
  For the wire data the replay text hides (actor, ability, target per
  option), a throwaway `crates/host/examples/scratch_*.rs` calling
  `describe::key` at decision N; delete it after (clippy --all-targets
  compiles examples).

## Traps

- `push.default=upstream` is set globally: a branch tracking `origin/master`
  pushed with `git push fork <branch>` lands on the fork's `master`. Push
  with an explicit refspec (`git push fork <b>:refs/heads/<b>`) and check
  `git config branch.<b>.merge` first.
- The owner may be mid-game on :5188: never edit the served checkout then
  (vite reloads the page, and the fork cannot rejoin yet: it fails the game
  on a closed socket and keeps the seat token in memory only, so a reload
  loses the game; the server would rejoin it, protocol.md §2, checked on a
  local server with `crates/server/tests/rejoin.mjs`, 2026-10-14). Work in
  a worktree under the job's tmp; fast-forward the checkout only when the
  admin API shows no live game (or the owner says so).
- After a vite restart the owner's tab can ask for long-deleted modules
  (EnginePassButton.vue, deleted 3 days earlier): a refresh fixes it.

## Where the engine/platform boundary leaked (to fix on the engine side)

What the fork infers today; each has its engine-board line and goes from
here when that line lands.

- Ability labels read from the English option text's tail (null with `text`
  off): options should carry a data label.
- An absent `actor` read as "your Methuselah" (War Ghoul): the protocol
  should say who uses an ability.
- A forced hunt (rules-qa 17.2) gave no reason: the fork infers it; a
  decision `reason`/prompt field would say it.
- Markers carried `n` but no name; minions of one name read alike until the
  text crate numbered them: the client needs data to tell them apart.

Fixed in the fork, not engine-side: a lone option taken at once, wrong for a
card's lone use.
